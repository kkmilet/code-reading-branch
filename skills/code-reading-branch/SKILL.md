# 代码阅读分支（code-reading-branch）

把一个陌生工程变成「知道怎么跑、知道从哪读、读得完、不走丢、改得动」的状态。

## 这个 Skill 解决什么

初级工程师接手项目时的真实困境不是"不会写代码"，而是四个具体故障：

1. **词汇故障**——卡在 `serializer`、`queryset`、`atomic`、`signal` 这类名词上，不是语法不会。
2. **层级故障**——分不清自己在看业务规则还是技术管道。
3. **跳转故障**——从 A 跳 B 再跳 C，回来忘了自己在哪。这是最致命的。
4. **边界故障**——不知道一段代码负责到哪结束，于是逐行读，读不完。

解决办法：一条覆盖主干的**阅读路线**、一张**一次请求的旅程图**、一个带**双向指针的注释分支**、一份**改动地图**。

## 一条主张：默认不讲，只标一句

大仓库里最伤人的不是"某个模块没读懂"，而是**注意力被平均分配**。所以默认动作是：

- **只把主干排成站**（6~8 站），站内文件精读 + 全档注释。
- **其余模块一律不进站、不注释**，只在 `READING.md` 的模块地图里占**一行**，写清「这是什么 + 不用关注」。
- 用户明确说"我想看 XX 模块"时才单独开一轮，不提前铺开。

判据：**如果不打算讲，就不要给它写注释、不要给它单独一节——多写一句都是干扰。**

**但"不讲"有边界**：砍掉的是与主干无关的模块，不是主干上的调用链。主干的控制流与数据流必须走完——只读"以后可能要改的文件"会让理解停在表层，改代码时容易漏掉组件之间的相互影响（依据见 `references/explain.md`）。

## 一条纪律：能删就删

"讲清楚"不等于"讲得多"。唯一判据：

> **删掉这句，读者会不会做错事？不会就删。**

三个冗余信号，出现就改：

1. 同一句话在两个文件里都写了一遍 → 删掉一处，留单一来源
2. 去掉专有名词后句子仍然成立（"这样更清晰""需要注意"）→ 删
3. 每站的理由都是同一个句式（"不先搞清 X，后面都是猜"）→ 在套模板，改成只在非显然时写理由

具体上限：文件头注释 6 行、函数头 2 行、行内 1 行、每站 3 行、旅程图下文字 2 句。见 `references/comments.md` 与 `references/route.md`。

**写和说都遵守 `references/voice.md`**：不铺垫、不总结已说过的、不用"首先/总的来说/值得注意的是"这类结构词、不堆抽象名词、不用比喻代替解释。判据同样是一句——读出声，像不像同事在讲话。

## 断点续读

用户隔一阵回来，**不要默认上下文还在**。先复述三句再继续：

> 上次走到第 5 站，讲了 `run` / `_run_stream` / `step` 三个方法，`READING.md` 已写完路线和旅程图。
> 接下来可以 ① 继续第 6 站 ② 重讲第 5 站 ③ 先看别的模块。

等他确认或纠正，再往下走。直接接着讲，会让用户在错误的前提上继续。

## 四条红线

1. **只读**：只新增注释行和 `READING.md`，不改业务代码、不加日志、不调格式。
2. **不执行**：不装依赖、不启动服务、不跑测试。启动结论靠静态证据推导。
3. **不猜**：推不出来的标 `【未知】`，不用"一般来说"填充。
4. **判"没有"前先枚举**：写"没有分布式事务""没有权限校验"这类**否定断言**前，必须先说明搜了哪些范围（目录 + 关键词）以及命中情况。**搜不到 ≠ 不存在**，没枚举就只写"未找到，搜索范围是……"。

## 什么时候不用

- 改代码 / 修 bug / 重构 → 通用编码能力
- 只解释一段粘贴的代码 → 直接答，不必起流程
- Code Review / 安全审计 / 工期评估 → 别的职责
- 项目超过 50 万行 → 先缩小到一个子项目或一条业务线

## 工作流

### S0 · 静默扫描

先看清对象，不打断用户。**只有一种情况允许问一句：目标路径本身有歧义**（路径下有多个清单文件，或它是一堆项目的父目录）——这时只问"看哪一个"，其余一律不问。

1. 确认目标路径：用户给的路径，否则用当前工作目录。默认按整仓处理。
2. 认栈：`manage.py`+`settings.py`→Django；`FastAPI(`→FastAPI；`go.mod`→Go；`package.json`→Node。细则见 `references/stack-recipes.md`。
3. 统计规模：源文件数、代码行数、顶层目录。忽略 `node_modules` `vendor` `dist` `build` `target` `.venv` `__pycache__` `.next` `coverage`。
4. 输出**一句话画像 + 一个选择题**，等用户回一个数字。

> 识别为 Django 4.2 + DRF + Celery，6 个 app，约 3.2 万行、187 个 .py 文件，最厚的是 orders（8.1k 行）。
> 你想怎么走？① 整体过一遍 ② 只搞 orders 这条线 ③ 先只把"怎么跑起来"搞清楚

回 ① 走默认路径；回 ②③ 缩小范围。**任何情况下路线都只覆盖主干，其余模块一行带过。**

### S1 · 还原启动链路

读 `references/runbook.md`，产出六段启动链，直接写进 `READING.md` 第 1 节，不在对话里大段复述。

每条必须带：证据位置（**不进站的文件写 `文件:行号`；站内文件写「文件 · 符号/字段名」**，因为注释会移动行号）+ 置信标签（`【文档明示】`/`【代码推断】`/`【未知】`）+ **"错了会看到什么报错"**。最后一项最重要——新手靠报错定位比靠描述快。

对话里只说一句："6 步写进导航了，第 4 步最容易卡（`pg_config`），要不要我先带你过一遍。"

### S2 · 出阅读路线（停点 1）

读 `references/route.md`，产出：

0. **先判项目形态**：Web 服务 / 库 SDK / CLI 工具，三者的站序不同（见 `route.md` 的表）。判错形态，整条路线都会别扭。
1. **模块地图**：覆盖**每一个**顶层目录，一行「这是什么 + 要不要看」。非主线写死「不用关注」，不留空白。
2. **站**：只排主干，按该形态对应的依赖方向，**6~8 站**，每站 **≤4 个文件**。
3. 每站写三项：**为什么排这**、**要读什么**、**读完你应该能说出什么**（一句话，不出题）。
4. 每个目录只有一个标注：`进站`（精读 + 全档注释）/ `不用关注`（一行说明，**零注释**）/ `别改`（第三方、生成代码，一行警告）。**不许出现"略读""后续可看"这类模糊词**。

进站的模块要克制：可进可不进的，一律不进站、只给一句话。用户想细看时再单独开。

然后停下等确认，允许用户回"按你的来"。

### S3 · 建阅读分支 + 写导航骨架

1. 前置检查：
   - `git rev-parse --is-inside-work-tree` 是否仓库
   - `git status --porcelain` 是否干净（脏了**停下**，让用户先 stash 或提交）
2. `git checkout -b reading/YYYYMMDD`
3. 建 `READING.md` 骨架：画像、启动链、路线、模块地图。旅程图、术语表、改动地图后续补。

不是 git 仓库：不建分支，改出 `READING/` 目录，注释以「文件:行号 + 应加内容」清单给出。

### S4 · 逐组写注释并讲解

按站推进，**一组 = 一站，每站 3~4 个文件**。顺序固定：

1. 写注释（格式见 `references/comments.md`）：**只写站内文件**，站外一律不注释。
2. **路径核实**：注释里每个 `文件:函数` 引用，落笔前 grep 到才算数；找不到只写函数名。
3. `git add -A && git commit -m "[READ] 第N组：<模块名>"`
4. 按 `references/explain.md` 讲解，讲完给 3 个选项。

**讲解必须遵守 `references/explain.md` 的四条**：

- 开头**报楼层**（L0 全景 / L1 模块 / L2 文件 / L3 函数 / L4 语句）
- 开头报**手上的数据形态**（原始 JSON / 校验后 dict / 实例 / 数据库行 / 响应）
- 跳转**只跨一层**，跳前说返回点，回来复述一次
- 一次讲解**最多跳 3 次**，超了就拆开讲

讲解用**三遍读法**组织：扫描遍（只看签名和文件头）→ 主链遍（跳过错误处理）→ 边界遍（异常/并发/缓存/权限）。

句子层面遵守 `references/voice.md`：一句一个事实、不铺垫、不总结已说过的、不用结构词（首先/总的来说）、不拿比喻代替解释。

再加两个动作：

- **先猜后验**：讲之前先让用户看签名猜用途，再验证。猜错的地方就是理解偏差。
- **说套路名**：认出分层 CRUD / 中间件链 / 事件监听这类惯用结构时，直接说出名字（见 `references/explain.md` 的套路表），比逐行解释更能帮用户分块。

**每组结束必须收一句**："这一组串起来是 A→B→C，数据从 X 变成 Y。" 少了这句，用户得到的就是碎片——这正是研究里"只读局部"为什么改不动代码的原因。

**每组结束给三个选项**：

> 下一步：① 进第 N+1 组 ② 深挖 `<某个函数或流程>` ③ 换个说法重讲这一组

### S5 · 写旅程图

完成前 2~3 组后（主链路已摸清），按 `references/journey.md` 写"一次请求的完整旅程"。

一条主链路；竖向编号步骤；每步标**「文件 的 符号」**（不写行号，注释会移动行号）+ 干什么；箭头旁标**传的是什么数据**；末尾标已知的坑。用 Mermaid `flowchart TD`，不用时序图。

两个补充：

- 发现 Celery / 队列 / 事件总线时，**不要另画一张图**，在主链末尾拉一条虚线异步分支，并写明"哪一步失败不影响主流程"
- 有 3 张以上互相关联的核心表时，补一张 `erDiagram`，只画核心 3~5 张

### S6 · 补交付物

规格见 `references/artifacts.md`。除路线和旅程，还要补六样：

1. **假设表**（3~5 行）：我的判断 / 依据 / 如果错了会怎样。每条都要能被用户一句话推翻。
2. **能力清单**：核心 3~8 条，每条五字段（一句话 / 什么时候用 / 最小片段 / 代码位置 / 高频度依据）。**星级必须有依据，写不出依据就不打星。**
3. **踩坑** 3~8 条，四段式（现象 / 原因 / 解决 / 如何避免）。现象要能搜到，**禁止编造报错文本**。
4. **最小调用片段** 5~15 行，照抄 README 或 `examples/`，标注来源，**不执行**。
5. **术语表** ≤15 条、**改动地图** ≥3 张卡片、**覆盖清单**（注了多少 / 总数 / 没读什么及理由）。
6. **过期说明**：什么时候需要重跑、什么时候不用。

只看单个模块时，换成 `artifacts.md` 里的**模块模式**六节，不要套整仓模板。

### S7 · 交付校验（四道闸门，缺一不过）

```bash
python scripts/verify.py        <repo>   # 只增不改：剥离注释后与基线逐字节比对
python scripts/check_refs.py    <repo>   # 引用可达：路径存在、符号真实、无同名歧义
python scripts/lint.py          <repo>   # 结构合规：站数/每站文件数/标签/卡片/术语条数
python scripts/comment_style.py <repo>   # 注释样式：行宽 ≤72、无符号、密度下限
```

三道全过才算交付。任何一道失败，修完重跑，**不要绕过闸门直接交付**。

```bash
python -m py_compile <改动过的 .py 文件>   # 可选：只编译不执行，确认注释没破坏语法
```

- `verify.py` 会自动读 `READING.md` 里的 `base_commit` 固定基线，避免主干前进后基准漂移
- `check_refs.py` 对**同名文件**（如 `tests/fixtures/agents.py` 与 `src/pkg/agents.py`）会报「无法确定指向」，此时必须补全为相对仓库根的完整路径
- `lint.py` 把「站数 3~8、每站 ≤4 文件、非主线必须写"不用关注"」变成硬检查
- `comment_style.py` 拦三类毛病：行太宽会折行、符号看不懂、只有表头没正文

### S8 · 全程一次总检（可选，不劝）

全部站走完后给 5 道题，一次问完，验"能不能把整个工程串起来"，不是"记不记得某个函数"。

答案默认折叠。用户答完逐题判（对 / 部分 / 错，指明缺哪句）→ 错的换比喻重讲 → 不重复原话。

用户说"不用考"就跳过，**不要劝**。

## 注释三档（摘要，完整规范读 references/comments.md）

| 档 | 写在哪 | 内容 | 上限 |
|---|---|---|---|
| L1 文件头 | **仅站内文件**，每文件 1 个 | 这是什么 / 谁调它 / 它调谁 / 改之前先看 | 12 行，每行 ≤72 宽 |
| L2 函数头 | 站内文件的公开函数 | 做什么 + 副作用 | 2 行 |
| L3 行内 | 主链路，或非基础语法处 | 这行为什么这么写 | 1~2 行 |

站外文件一个注释都不加。它们只在 `READING.md` 模块地图里占一行。

**每行都要带 `[READ]` 标记。** 只在首行标，续行会在剥离时留下残行，`verify.py` 直接不通过。

**引用写「符号名 + 完整相对路径」，不写行号**：`Model.generate()，在 src/pkg/models.py`。注释会移动行号，写死的行号在你写完那一刻就失效；短文件名遇到同名文件会跳错。

**不用符号**：框线 `──`、箭头 `←→`、间隔点 `·`、圈号 `①②③` 一律不写，标签用「谁调它 / 它调谁 / 改之前先看」。这些符号不承载信息，读的人还要先猜方向。

**硬规则：注释独占整行，绝不修改任何代码行。** 插入按行插，不要字符串替换（会把注释粘到代码行尾）。

**密度下限**：每个站内文件至少 1 条 L1 加 2 条 L2/L3。只写表头，等于给了封面没给正文。

## 降级表

| 情况 | 处理 |
|---|---|
| 不是 git 仓库 | 改出 `READING/` + 注释清单，不动源码 |
| 工作区有未提交改动 | 停下，列出来，让用户先 stash 或提交 |
| 分支重名 | 加时间后缀，不覆盖 |
| 站内文件 >32 | 分两批，一批一 commit，每批独立校验 |
| 用户要求「多讲点模块」 | 先问清是"都要讲"还是"只标一句"；默认只标一句，别顺手铺开 |
| 认不出框架入口 | 明说"未识别到框架"，改按目录结构推断 |
| 单文件 >1000 行 | 只注文件头 + 函数签名区，正文给分段索引 |
| monorepo 多栈 | 先问先看哪个子项目，逐个跑 |

## 交付前 12 条自检

前四项由脚本判定，不用嘴说：

1. `verify.py` 通过——剥离注释后与基线逐字节一致
2. `check_refs.py` 通过——没有跳不过去的引用
3. `lint.py` 通过——结构、站数、标签、卡片、术语条数达标
4. `comment_style.py` 通过——行宽不超 72、没有符号、每个文件都有正文注释

其余靠自查：

5. 站数 3~8（目标 6~8），每站 ≤4 个文件；需要解释顺序的站写了理由，且不超过 3 站
6. 模块地图覆盖每一个顶层目录，非主线都写了「不用关注」
7. **站外文件零注释**
8. **每组讲完有一句"本组链路串起来是……"**（否则就是 as-needed 的碎片阅读）
9. **能力清单**核心 3~8 条、每颗 ★ 都有可核查依据；**踩坑** 3~8 条、四段齐全
10. **假设表**至少 3 行且每条可被一句话推翻；所有否定断言都写了搜索范围
11. 术语表 ≤12、改动卡片 ≥3、最小片段标注了来源、写了过期说明
12. `READING.md` ≤180 行；无"一般来说 / 总的来说 / 值得注意的是"这类空话、无编造报错、无自造统计
