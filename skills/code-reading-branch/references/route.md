# 阅读路线与改动地图

路线回答：**这 187 个文件，按什么顺序读，才能走完且不走丢。**

## 一、注意力预算（比排站更重要）

- 总站数 **6~8**（硬边界 3~8），每站 **≤4 个文件**。超了就是在稀释注意力。
- 站数的算法：`ceil(主干文件数 / 4)`，再夹到 3~8。主干文件 = 入口 + 核心 service + 数据模型 + 配置。
  主干文件超过 32 个时，**不加站**，改成两轮读（第一轮只走 L1 契约，第二轮再进 L3）。
- 一个目录能不能进站，只问两句：**主干请求会经过它吗？改动会先撞到它吗？** 两个都否 → 只给一句话。
- 宁可少排一站，也不要为了"覆盖完整"硬塞。

用户说"我要读整个工程"，正确理解是：**主干全部精读 + 其余全部知道是什么**，不是每个模块都精读。
逐模块精读的结局是每个都读了、每个都没记住。

## 二、模块地图（先做这个）

覆盖**每一个**顶层目录——留一个空白目录，用户就会在那里迷路。但覆盖 ≠ 展开：**每个非主线目录只占一行，多一个字都不写。**

```markdown
| 目录 | 这是什么 | 要不要看 |
|---|---|---|
| `config/` | 全局配置、路由总表、WSGI 入口 | 进站（第 1 站） |
| `apps/orders/` | 下单、支付、售后，全项目最厚 | 进站（第 3 站） |
| `apps/users/` | 登录注册、权限 | 不用关注（要改权限时再单独看） |
| `apps/common/` | 分页、异常、响应包装 | 不用关注 |
| `apps/tasks/` | Celery 异步任务 | 不用关注（除了库存对账那个） |
| `scripts/` | 运维脚本，不在请求链路上 | 不用关注 |
| `third_party/` | 第三方 SDK 拷贝 | 别改（升级时整体替换） |
```

只有三档，不要发明第四档：

| 档 | 含义 | 用户实际会做什么 |
|---|---|---|
| **进站** | 主干，必读 | 四层讲解 + 全档注释 |
| **不用关注** | 知道它在就行 | 读那一行，**不做任何事** |
| **别改** | 第三方、生成代码 | 读那一行，别碰 |

`不用关注` 必须**真的写"不用关注"**。不要写成"略读""后续可看""有时间再看"——那些词会让用户以为以后要读，于是分心。
这是这条规则的全部意义：**帮用户决定"不读什么"**。

## 三、站的排法

**顺序永远按依赖方向，不按目录顺序。** 但"依赖方向"在不同形态的项目里长不一样，先判形态：

| 项目形态 | 判定信号 | 站序 |
|---|---|---|
| **Web 服务** | 有路由、有 `app.run` / `manage.py` / `*Handler` | 配置 → 数据模型 → 业务核心 → 接口层 → 入口/路由 |
| **库 / SDK** | 有 `[project.scripts]`，或 `__init__.py` 大量导出，没有 HTTP 入口 | 公开 API → 数据契约 → 核心抽象 → 主循环 → 外围能力 |
| **CLI 工具** | 只有命令行入口 | 命令注册 → 核心流程 → 输入解析与输出 |
| **多服务 monorepo** | 多个 manifest、多个 `cmd/` | 先选一个子项目，按上面某一种排 |

判错形态，整条路线都会别扭：把库当 Web 服务排，会在"配置"和"接口层"上耗掉一半时间，而真正的主循环排在最后。

理由：配置决定连哪个库、有哪些外部服务；数据模型决定有哪些概念；业务核心是价值所在；接口层只是包装。反过来读，你会一直在猜"这个字段哪来的"。

每站**最多 3 行**，多一行就是在写报告：

```markdown
### 第 2 站 · 订单数据模型（约 40 分钟）

**为什么排这**：状态枚举只在这里定义，第 3 站全靠它。
**要读**：`apps/orders/models.py`、`apps/orders/migrations/0001_initial.py`（只看字段，不看变更历史）
**读完你应该能说出**：订单有哪几个状态、怎么流转、和支付/库存什么关系。
```

第三项是**路标，不是考题**——一句话，不给答案，不打断。

「为什么排这」限 **20 字**，且**不许套模板**。三个信号说明你在套模板：

- 每站都是「不先搞清 X，后面都是猜」
- 理由能原样搬到另一个项目的同一类模块上
- 理由说的是"重要性"（"这是核心"），不是"为什么排在这个位置"

顺序按依赖走是显然的时候，理由可以不写。**七站里最多三站需要解释顺序**，其余靠"依赖在前"本身就够了。

## 四、每站的读法（三遍）

同一站内部按三遍走，不要一次读懂：

1. **扫描遍**：只看文件头注释 + 函数签名 → 这个文件对外提供什么
2. **主链遍**：只看主链路函数体，跳过错误处理 → 请求怎么走
3. **边界遍**：异常、并发、缓存、权限 → 改的时候踩什么

细则见 `references/explain.md`。

## 五、改动地图（二开的核心）

"改 X 先看 Y"只解决定位，不够二开。二开要知道四件事：**改哪几处、什么顺序、影响谁、怎么验**。

每张卡片固定四要素：

```markdown
### 给订单加「备注」字段
1. `apps/orders/models.py` — 加字段 + 生成迁移     ← 先做，否则后面全报错
2. `apps/orders/schemas.py` — 加字段               ← 不加，API 收不到
3. `apps/orders/services/order.py` — create() 透传  ← 不加，值会丢
影响面：订单列表接口 / 导出 CSV / 对账脚本（是否读备注：待确认）
验证：`tests/test_order_create.py::test_create`
风险：迁移上线要考虑存量数据的默认值
```

挑卡片的办法：从路线里挑 3~5 个**最可能被要求改**的地方。判据：

- 需求里最常出现的词（订单、支付、权限）
- `git log` 最近三个月改动最频繁的模块
- 名字里带 `service` / `handler` 的核心文件
- 用户在 S0 明确说的业务方向

至少写 3 张。写不出 3 张，说明路线还没读透。

**顺序很重要**：卡片里必须排出"先改哪个"。顺序错了，用户改完第一个就跑不起来。

## 六、反例

| 反例 | 为什么错 |
|---|---|
| 20 个模块全排进站 | 注意力被平均分配，每个都读一半 |
| 按目录字母序排（`apps/` → `config/` → `scripts/`） | 这是文件管理器，不是路线 |
| 按代码量排，最大的先读 | 大不等于重要，`utils.py` 常常最大也最没营养 |
| 把"不用关注"写成"略读" | 用户以为以后要读，于是现在也放不下 |
| 给站外目录写注释 | 分支噪音翻倍，用户打开 IDE 就烦 |
| 每站都要"确认" | 读 12 站要确认 12 次，用户会关掉你 |
| 改动卡片只写"改 service.py" | 没说顺序和影响面，等于没说 |
