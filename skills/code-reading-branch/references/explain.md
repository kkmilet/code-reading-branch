# 讲解方法

这份文件决定「用户能不能读明白」。讲解前必读。

## 依据：为什么是这几条规则

不是凭感觉定的，每条都有出处（见文末）。四条最关键的：

1. **只读"要改的地方"会留下弱心智模型。** Littman 等人的实验里，采用 as-needed 策略（只读与当前任务相关的代码）的人，改代码时更容易失败——他们只拿到静态知识，漏掉了组件之间的因果交互。采用 systematic 策略（顺着控制流和数据流走完整条链）的人建立了强心智模型。
   → **所以主线必须追控制流和数据流，不能只读"我以后可能会改的那几个文件"。**

2. **专家靠"信标"和"惯用套路"分块。** Brooks 把可识别的代码特征叫 beacon（比如看到嵌套循环里交换两个元素，就猜到是排序）；Soloway 和 Ehrlich 把成型的代码片段叫 plan。识别得越快，读得越快。
   → **所以要显式说出"这是哪种套路"，让用户能把新代码挂到已知结构上。**

3. **人的阅读顺序更接近控制流，而不是行号顺序。** 眼动实验显示，按控制流预测阅读顺序比按行号准；而且新手比老手更倾向于线性读。
   → **所以路线按请求链路排，不按目录名、不按文件顺序。**

4. **工作记忆容量有限。** 一次塞进太多跨文件跳转，前面读的就掉了。
   → **所以单次讲解只跨一层、只开 1 跳窗口。**

## 四个故障与对应解法

| 故障 | 表现 | 解法 |
|---|---|---|
| 词汇 | 卡在 `serializer` / `queryset` / `atomic` / `signal` | 首次出现就地展开 2~3 句 + 记进术语表 |
| 语法 | 看到 `with` / `yield` / 推导式 / 装饰器，不知道这行在干嘛 | 就地一行，说明它**在这里**做什么，不讲语法定义 |
| 层级 | 分不清在看业务规则还是技术管道 | 每段开头**报楼层** |
| 跳转 | 从 A 跳 B 跳 C，回来忘了在哪 | **单层跳转 + 显式返回点 + 跳转预算** |
| 边界 | 什么都想读，逐行读 | **三遍读法**，第一遍主动跳过实现 |

## 一条总则：局部要窄，全局要连

这两件事经常被做反：**要么钻一个函数出不来，要么浮在目录结构上不进代码。**

- **局部窄**：讲一个函数时只开 1 跳窗口——当前函数 + 直接上游 1 层 + 直接下游 1 层。三层以外不读。
- **全局连**：**每讲完一组文件，必须把这一组用控制流串一次**，一句话说完"这一组的链路是 A→B→C，数据从 X 变成 Y"。

只做前者 = as-needed，读得再多也是碎片；只做后者 = 只认识目录，不会改代码。

**这条也是"默认不讲"的边界**：不讲的是与主干无关的模块，不是主干上的链路。砍掉旁支，是为了把因果链追完。

## 五层模型（报楼层）

| 层 | 看什么 | 典型问题 |
|---|---|---|
| **L0 全景** | 业务、模块、外部系统 | 这需求该不该在这个系统里改 |
| **L1 模块** | 职责边界 + 对外契约 | 加接口影响谁 |
| **L2 文件** | 这个文件在模块里的角色 | 入口在哪个文件 |
| **L3 函数** | 输入 / 输出 / 副作用 / 分几步 | 这个函数在干什么 |
| **L4 语句** | 这几行为什么这么写 | 改这个判断会怎样 |

规则：

- 每段讲解**第一行**写清楚在第几层、哪个文件、哪一行。
- 默认停在 **L3**，多数阅读在这一层完成。
- 下到 L4 必须有理由（用户在改这段逻辑，或这行有坑）。
- 回到 L1 讲契约前，先明说"我们退回去看整体"。

（熟悉 C4 模型的话：L0 对应系统上下文，L1 对应容器/模块，L2/L3 对应组件与代码级，L4 在 C4 之下。）

## 三条跳转规则

### 1. 只跨一层

允许：L3 函数 → 另一个文件的 L3 函数（同层跨文件）。
允许：L3 → L4（向下钻同一个函数）、L3 → L1（向上回退看契约）。
不允许：从 `views.py` 的 L3 直接扎进 `repository.py` 的 SQL（L4）。中间隔着一个 service，跳过去就断链。

### 2. 显式返回点

跳出去之前必须说，回来之后必须复述：

> 我们刚在 `create()` 的第 2 步，现在跳到 `inventory.reserve()` 看它扣库存。
> **记住回来接第 3 步：把 Order 实例序列化返回。**

回来时：

> 回到 `create()` 第 3 步。刚才 reserve() 干的事是：调库存服务，超时 3 秒，失败抛 `InventoryError`。

这两句话就是"上下文栈"的 push 和 pop，不能省。

### 3. 跳转预算：一次最多 3 跳

超过 3 跳说明这个函数太大或耦合太重。处理方式：

1. 先只讲它的**契约**（给什么、返什么、抛什么），不进去
2. 告诉用户"这个函数建议单独开一轮讲"
3. 把内部跳转画成旅程图的子链路，不线性讲

## 三遍读法（每站都按这个顺序）

| 遍 | 只看 | 明确不看 | 产出 |
|---|---|---|---|
| **扫描遍** | 文件头注释、函数签名、目录结构 | 任何函数体 | 这个模块对外提供什么 |
| **主链遍** | 主链路函数体 | 错误处理、参数边界、日志、缓存 | 一次请求怎么走 |
| **边界遍** | 异常、并发、缓存、权限、软删除、幂等 | 无关模块 | 改的时候会踩什么 |

**第一遍的任务不是"读懂"，是"知道有这个东西"。** 初级工程师最常犯的错，是第一遍就想搞懂每一行，然后在第一个 `try/except` 里卡死。

## 先猜后验（用信标加速）

读一个函数前，先用签名和注解猜它干什么，再去验证。猜错比不猜收获更大——错的地方就是你理解偏差的地方。

```
看到：@transaction.atomic + def create(self, data) + 返回 Order
先猜：写库、要事务、失败会整体回滚
验证：看函数体里有没有 save()，事务范围到哪一行结束
```

## 常见套路（plans）：看到这些形状，直接归类

| 看到什么 | 大概率是 | 读它时只关注 |
|---|---|---|
| router/urls → view/handler → service → repository | 分层 CRUD | 校验、业务、持久化各自在哪一层 |
| 中间件链 / 装饰器堆叠 | 横切关注点 | **顺序**和放行条件 |
| `*Serializer` / DTO / schema | 输入输出契约 | 必填项、默认值、类型转换 |
| `*Service` + 注入 | 业务编排 | **事务边界**、副作用 |
| repository / DAO / Mapper | 数据访问 | 表映射、查询条件 |
| signals / hooks / listeners | 事件副作用 | 谁监听、失败会不会影响主流程 |
| task / worker / consumer | 异步 | 触发点、重试、幂等 |
| strategy / factory / registry | 扩展点 | 新增实现要注册到哪 |

说出"这是哪种套路"本身就在帮用户分块——比逐行解释有效得多。

## 三个降低认知负荷的手法

### 单概念原则

一个函数最多引入 **1 个**新概念。同时出现 serializer、事务、信号三个新东西时，只展开第一个，另外两个记进术语表、留到后面站。

语法解释不占这个概念配额——遇到非基础语法必须解释，哪怕同一段已经讲过一个术语。

"新概念"= 外行第一次见的技术名词（`serializer`、`依赖注入`、`中间件`、`信号`、`事务边界`、`幂等`、`乐观锁`）。项目自己的业务名词（订单、SKU）不算，但要进概念地图。

### 1 跳窗口

见"总则"。注意它是**单次讲解**的窗口，不是"整个项目只读这么点"。

### 追数据，不追分支

始终标"现在手上的数据是什么形状"：

```
原始 JSON → 校验后的 dict → Order 实例 → orders 表的一行 → 响应 JSON
```

代码的主线是**数据在变形**，分支是变形失败的兜底，不是主干。讲的时候每步都带一句"手上现在是 `<形态>`"。

## 讲解模板（每个函数都用这个骨架）

```
第 2 站，第 3 个文件，L3 函数
orders/views.py 的 post()
在哪：orders 模块，接口层，请求入口
手上数据：request.data，原始 JSON
契约：给 JSON，返回 201 加订单详情；校验失败返回 400
步骤：
  1. 造 serializer 校验，失败就在这里返回，不往下走
  2. 转交 service.create()，下一跳，看完回来接第 3 步
  3. 序列化返回
注意：事务在 service 里，这里没有
```

四个字段缺一不可：**楼层 + 数据形态 + 契约 + 步骤**。

## 反例（出现即不合格）

| 反例 | 为什么错 |
|---|---|
| 一上来贴 60 行代码逐行翻译 | 用户失去全局，读到第 10 行忘了第 1 行 |
| 从 view 直接讲 repository 的 SQL | 跨了两层，中间契约没交代，断链 |
| 讲完不回收，不报"现在回到哪" | 用户不知道自己在哪 |
| 一个函数里展开 3 个新概念 | 认知超载，一个都记不住 |
| **只讲"用户以后要改的那些文件"** | 这就是 as-needed，会漏掉组件交互，改代码时出错 |
| 用"一般来说""通常这样"补空白 | 无证据断言，会误导 |
| 讲完不给下一步 | 用户不知道该问什么（所以给 3 个选项） |

## 「为什么这么设计」怎么答

静态看代码答不出设计动机，只能考古。给用户可执行的查法，别编故事：

```bash
git log -S"order.created" --oneline -- apps/orders   # 谁引入了这个关键字
git log --oneline -20 -- apps/orders/services/order.py
git blame -L 40,80 apps/orders/services/order.py
```

- 找到 → 给 commit hash + 一句话，让用户自己点进去看
- 找不到（历史被压缩、仓库是浅克隆）→ 标【历史不可考】，**不要猜**

## 二开导向：讲完给一次「改动预演」

每讲完一个模块，加一句预演，**不给答案、不判分、不等回答**：

> 预演一下：如果给订单加一个「备注」字段，你要动哪几处？往下读的时候可以自己对。

用户心里过一遍，读到 `schemas.py` 时会自动对上"哦，这里要加"。这是从"读懂"到"改得动"最便宜的桥。

预演只出**本模块范围内能答的**，不跨到还没讲的模块。

## 与注释的分工

- **注释**：长期留在代码里，回答"这是什么、从哪来、到哪去"。要短。
- **对话**：一次性，回答"为什么、怎么串、我该看哪"。可以长。

不要把对话里的长篇解释塞进注释，也不要把注释能说清的（比如上游是谁）在对话里重复三遍。

## 出处

- Littman, Pinto, Letovsky, Soloway：systematic 与 as-needed 两种阅读策略；as-needed 只形成弱心智模型，改代码时更容易失败。
- Brooks (1983)：以信标（beacons）为核心的假设驱动理解模型。
- Soloway & Ehrlich (1984)：编程套路（plans）与话语规则。
- Busjahn et al. (2015)：眼动研究，阅读顺序更接近控制流而非行号顺序；新手比老手更线性。
- Pennington (1987)：先形成控制流抽象，再形成功能抽象。
